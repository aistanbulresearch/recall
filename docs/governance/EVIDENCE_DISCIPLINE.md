# Evidence Discipline Rules (owner directive, 2026-08-24)

Owner: "Bir erratum kabul edilebilir; repoda 4-5 duzeltme olursa isin kredibilitesi duser. Dersleri cikar, tum agentlar bilsin."
Scope: every lane, every run, every evidence or governance document, until submission.
Repo copy: this file mirrors the director's `.remember/evidence-discipline.md`
master. Its 17-rule count is derived from the numbered rule headings at copy
time rather than copied from stale prose.

## The 17 rules

1. NO FREE-STANDING DECLARATION FIELDS. Any field that describes an artifact's own meaning (primary arm, protocol version, evidence scope, schema version) is derived from the governing document or the locked config at write time. A constant in code that restates a governing document is a defect waiting for the document to change. (Source: ARM_DECLARATION stale after Amendment 001; RegistryResolutionReceipt 1.0.0 after core moved to 1.1.0.)

2. CHANGE SWEEP. When a governing document changes (amendment, contract version, decision), the change author immediately greps every surface that could restate it: code constants, manifests, docs, UI copy, tests. The sweep result (paths checked, hits fixed) goes in the change report. A change is not done when the document is edited; it is done when nothing else contradicts it.

3. NO UNMEASURED NUMBER IN AN EVIDENCE DOCUMENT. Compute first, then write. Never write a figure from memory or plausibility and verify later. Before any evidence document is committed, every numeric claim in it is re-derived from the artifact or from git, and the check is stated in the report. Enforceable form (L1, 2026-08-25): a count appears in a message only with the command that produced it in the same message; otherwise the list itself is the claim. "A number I cannot show the derivation for is a guess wearing a measurement's clothes." Inherited numbers are re-derived before repeating - the total is the part quoted without the breakdown behind it. (Sources: "2,847 leaves" written unmeasured, true count 947; "37 paths" eyeballed by L1, propagated by the director with his own contradicting uniq -c in the same message, true count 39.)

4. STARTUP ASSERT COVERS DECLARATIONS TOO. The locked-configuration assert before a frozen or permanent action covers measurement parameters AND declaration fields. Mismatch aborts before any work. (Extends the 08-23 rule that caught num_predict living only in a CLI flag.)

5. DERIVED VIEWS ARE MACHINE-MADE AND SELF-REFUSING. A corrected or derived artifact is produced by a published script from the immutable original; the script refuses to write if anything outside its declared correction set differs, and the output carries authoritative: false plus the original's hash.

6. PROVENANCE OF GATE INPUTS. Every input to a pass/fail gate declares which source (which arm, which path, which run) produced it. An unlabeled gate input is a defect even when the current values make it moot. Extension (L3, 2026-08-25): running the thing is necessary but not sufficient - a run faithfully returns whatever a fixture put there, so OUTPUT IS NOT PROVENANCE; "what came out" and "did anything compute it" are separate questions, and a displayed value carries its data_mode/source so a fixture constant can never read as an observed fact. (Sources: comparison_escapes derived from arm A alone, undeclared; resolution_mode read from a demo fixture literal and reported as "what a run returns".)

7. GREEN MEANS GREEN AT THE TARGET. No lane reports green from its own branch alone: run against the integration target's contract version and a dependency-synced interpreter, and separate code failure from environment gap before naming a cause. Corollary (L3, 2026-08-25): a green reported FOR A COMMIT is measured on a clean checkout of that commit - the gate run in the worktree where you are editing cannot detect a file you forgot to stage; only a clean checkout can. "Green from committed blobs" is a claim about the commit, so the run must read only the commit. (Sources: two red merges on 08-23; registry.ts unstaged at e5137c1 while the suite passed off the working tree - a clean checkout would not have built.)

8. COMMIT BEFORE RUN, PREDICT BEFORE RUN. Configuration and preregistration are committed before the run starts; measurable predictions with numeric thresholds are committed before any corrective rerun; failure of the prediction means elimination, not another iteration.

9. EXTERNAL CALLS ARE BOUNDED. Every non-interactive external call (gcloud, HTTP, model) carries a timeout, and termination kills the process TREE. Flags are not the fix. Orphan checks run before and after. (Source: 49-hour hung token processes.)

10. RECEIPTS FOR INSTRUCTIONS. Every instruction to an agent is acknowledged with "Alindi: <label>"; every director-bound report goes through SendMessage, not terminal output. A referenced instruction whose text never arrived means: read the authoritative artifact, act on it, and say the text never arrived.

11. EVIDENCE HASHES ARE CLAIMS ABOUT THE BYTES A READER RECEIVES. Verified against the committed blob, never the working tree. Any path whose sha256 is declared in a manifest, approval, or erratum is marked -text so version control preserves its exact bytes. Freezing an artifact includes a fresh-checkout reproduction check: sha256 over `git cat-file blob` of the committed object equals the declared value, demonstrated as an equality in the report rather than asserted. A path that becomes hash-bound later is added to the exemption at the moment its hash is first declared - the defect arrives when a file becomes hash-bound, not when it is created. Byte-faithful paths declare whitespace=cr-at-eol, and pure evidence artifacts are additionally -diff, so integrity tooling reads them as the opaque bytes they are; making a file byte-faithful changes how every text tool sees it, so the tooling that reads it is part of the change, not a consequence to discover later. (Source: 2026-08-24, eol=lf normalization made every declared frozen-chain hash unreproducible from checkout; caught by the L2 integration gate at blob level after every lane, director included, had verified only working-tree bytes.)

12. POWERSHELL 5.1 ENCODING DEFAULTS ARE HOSTILE TO BYTES. Windows PowerShell 5.1 inserts BOMs and re-encodes by default: piping into a native command's stdin, Set-Content/Out-File with -Encoding UTF8, and console output on non-UTF-8 codepages. Any byte-sensitive value written from PS 5.1 goes through explicit .NET APIs with BOM-free encoding ([IO.File]::WriteAllBytes or UTF8Encoding($false)); any file read back for comparison is read as utf-8-sig; and a value destined for strict decoding (base64, hashes) is never routed through the 5.1 pipeline. (Incidents: capability secret v1 BOM via pipeline; diagnostic outcome file BOM via Set-Content; corrupted printing on the Turkish-codepage console. One rule instead of three lessons.) Canonical citation, measured same string, same shell, same call site: `Set-Content -Encoding UTF8` -> `ef bb bf 45 52 52` (BOM present); `[System.IO.File]::WriteAllText(X, V, (New-Object System.Text.UTF8Encoding($false)))` -> `45 52 52 4f 52 3a` (no BOM). The utf-8-sig read stays as belt and braces, not as the fix: fixing the symptom and shipping the cause is not a fix.

13. PROVISIONING IS PART OF THE GATE'S ENVIRONMENT. A suite is green only in the environment the gate runs, and provisioning is part of that environment. Present-but-unlinked dependencies fail like missing ones while looking installed, so verify by running the gate's own command in the gate's own checkout, offline. (Source: 2026-08-25, core web/node_modules held the pre-import link set while the store and lockfile were complete; the only symptom was a tool reaching for the network. Same shape as the eol defect one layer up: the artifact was correct, the thing presenting it to the tool was not. Fix mechanism of record: `pnpm install --offline --frozen-lockfile` in the gate checkout - resolves from the machine store, reproducible from the lockfile, idempotent.)

14. A DEPLOYED ARTIFACT'S IDENTITY IS PROVEN BY INTERROGATION, NOT METADATA. Display names, service accounts, resource ids, catalog rows, and deploy records are all statements ABOUT an artifact; none is testimony FROM it. Before any deployment is reported COMPLETE, the running artifact is asked who it is and the answer is asserted against the claim. (Source: 2026-08-25, three Agent Engine deploys raced on the SDK's fixed staging path gs://<bucket>/agent_engine/agent_engine.pkl - last writer won, three engines with correct names/SAs/ids all ran the same agent, every gate green, fleet a fiction. Caught because payloads carry an author field by design - provenance discipline, not a deploy gate, found it. Companion lesson: remove a race, do not narrow it - per-member gcs_dir_name kept the concurrency and deleted the shared mutable path. L1's formulation of record: "A fleet gate that never asks an engine who it is will pass a fleet of clones every time." Corollary, from building the guard itself: the guard's READING SURFACE is part of the guard. observed_authors reads the event mappings, not a serialised dump - json.dumps(default=str) yields a repr whose quoting makes an '"author"' probe find a clean absence rather than a failure; the first probe reported "authors: none" against an engine that had just stated its author in plain text. A test asserts the repr trick finds nothing while the real reader finds the author. "A guard that reads the wrong surface reports innocence." And the assertion needs both conjuncts: every engine is itself AND no two are the same one - per-engine correctness alone passes a lucky fleet, distinctness alone passes three different wrong agents.)

15. HOLDING MEANS THE REPORTED HEAD DOES NOT MOVE. A "settling point" or "final HEAD" report is a commitment: any commit made after it invalidates it, and the lane RE-REPORTS before anyone consumes the old number. Integrators merge the reported ref and are right to; the stale number is the reporter's defect. Consumers of a reported HEAD ask the lane to confirm it is still current before treating it as final - a declared reconciliation is a question to the lane, not a statement by the reader. The rule applies to EVERY commit, including documentation - a merge parent does not know the difference; the exception feels harmless because of what it contains, and the mechanism does not read contents. Completeness of a lineage is proven by exhaustion (rev-list lane ^certificate), not by two people agreeing about a chain neither enumerated. (Source: 2026-08-25, L1 reported HEAD 3a153d7, then committed the evidence index at 3b45770 without re-reporting - "I thought of it as documentation, which felt outside the thing being held"; the merge correctly took 3a153d7 and the certificate shipped without the index the package cites. Causation order of record: the auditor's condition was well-aimed, the lane's report was stale, the director's declaration was premature. Found because the director asked the lane to check the lineage instead of declaring it resolved - after first declaring it resolved.)

16. WINDOWS SHELLS SILENTLY REWRITE ARGUMENTS; A MANGLED COMMAND'S EMPTY OUTPUT READS AS A CLEAN NEGATIVE. In Git Bash on Windows, MSYS path conversion mangles `git show <branch-with-slash>:<path>` (slash becomes backslash, colon becomes semicolon); git exits 128, and a grep over the error text finds nothing - absence-of-match masquerading as absence-of-rule. Any ref containing a slash is affected; bare shas are not, which makes the failure intermittent and therefore more credible. Use the sha, `git show <ref> -- <path>`, or `git cat-file`. General form: on Windows, a command that can be silently rewritten by the shell layer is not a measurement until its exit code and raw output are read; when two measurements disagree, find which one is lying instead of keeping the one that fits. (Source: 2026-08-25, L3 stated a false finding - "core lost the governance line" - from a grep over MSYS-mangled git output; caught because the diff contradicted the grep. Companion to rule 12: the Windows shell toolchain is hostile to byte and path fidelity in more than one layer.)

17. AN ACCEPTANCE CRITERION THAT CANNOT BE SATISFIED AS WRITTEN IS A CONTRACT DEFECT, NOT A PERMANENT FAILURE. When measurement proves a criterion unsatisfiable (a row that can never be marked passed, or a behaviour the document itself contradicts elsewhere), the criterion is rewritten to state what is actually enforced and by which layer, with not-exercised rows named and referenced - it is not carried as if satisfiable, and it is not silently treated as forever-unmet. Reconciliation sweeps cover acceptance/criteria lists, not just prose. (Source: 2026-08-25, auditor's formulation after L1 found the gateway contract's acceptance item carried verbatim while two of its five clauses were unsatisfiable as measured - expired-token permanently NOT ISOLATED, wrong-audience refused by the application layer, not the perimeter; caught before any sign-off.)

## Standing verification habit

Before committing any evidence or governance document, the author runs a self-check and states it in the report: (a) every number re-derived, (b) every hash freshly computed, (c) every cross-reference (commit ids, file paths, section numbers) resolved against git, (d) change sweep done if a governing document moved. The report names what was checked, not just "verified".

Why naming-what-was-checked is the load-bearing half (L3, 2026-08-25): instruments answer the question they can see, not the question asked, and no one can tell the difference from inside - a grep that cannot see across a line wrap reports absence identically for real absence and unseeable presence; a claim narrowed on a fragment of the evidence reports a narrower truth than the facts support; a hedge can be false too. What makes these recoverable is DISCLOSURE, not detection: "the corrections were not caught by better checking; they were caught by saying out loud what the check actually covered" - each party's disclosure was the other's fix. Also: attribution of internal verification belongs in the commit message, not the public prose - a reader can check WHAT and WHEN; naming WHO converts a checkable claim into an appeal to authority.
